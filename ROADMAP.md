# Roadmap развития `as-flight-proxy` (`v0.2.0` – `v0.5.0`)

Текущий релиз **`v0.1.0`** закрывает полный цикл высокоскоростной параллельной записи из Spark 3.5 (PySpark / Scala) в Aerospike 8+ CE, умные по-ключевые ретраи перегрузки, координацию статуса через Raft с TTL и режим пост-записной DQ-валидации (включая `NaN == NaN`).

Ниже представлен план развития системы на следующие **4 релиза**.

---

## Релиз `v0.2.0` — Высокоскоростное чтение из Aerospike в Spark (`SupportsRead` / `DoGet`)

Сейчас коннектор реализует запись (`SupportsWrite` / `DoPut`). Следующий ключевой шаг — сделать полноценный коннектор чтения `spark.read.format("aerospike-flight")` поверх Arrow Flight `GetFlightInfo` + `DoGet`.

### Что планируется реализовать:
1. **Параллельное сканирование партиций Aerospike (Partitioned Scan)**:
   * В Aerospike данные равномерно распределены по `4096` партициям.
   * При вызове `GetFlightInfo` на `proxy_server` прокси делит `4096` партиций на `N` диапазонов (по числу Spark-партиций `connector.readPartitions`) и возвращает список `FlightEndpoint` с `Ticket`-ами, распределёнными по всем живым нодам прокси-кластера из Raft.
   * Экзекьюторы Spark параллельно вызывают `DoGet(Ticket)` к назначенным нодам прокси, которые сканируют свои диапазоны партиций Aerospike и стримят `RecordBatch` обратно в Spark.
2. **Пакетное чтение по списку ключей (Batch Key Lookup / Join)**:
   * Поддержка вычитки конкретных ключей через `BatchRead` (или через `DoExchange`), чтобы эффективно обогащать небольшой/средний DataFrame в Spark данными из Aerospike без полного сканирования сета.
3. **Projection & Predicate Pushdown (`SupportsPushDownRequiredColumns`, `SupportsPushDownFilters`)**:
   * Передача в Aerospike только запрошенных в `df.select(...)` колонок (`Bins::Some(...)`), чтобы не гонять лишние бины по сети.
   * Проброс базовых фильтров Spark (`=`, `>`, `<`, `IN`, `BETWEEN`) в выражения фильтрации Aerospike (`FilterExpression`).
4. **Автоматический вывод схемы (`inferSchema`) и пользовательская схема (`.schema(...)`)**:
   * Сэмплирование нескольких записей из сета Aerospike для автоматического построения `StructType` в PySpark, либо чтение строго по заданной схеме `spark.read.schema(my_schema).format("aerospike-flight").load()`.

## Релиз `v0.3.0` — Расширенные операции записи, пер-строчный TTL и сжатие трафика

В реальных продуктовых пайплайнах часто требуется не просто перезаписать бин, а атомарно модифицировать структуру (CDT), прибавить счётчик или задать индивидуальный TTL для каждой строки.

### Что планируется реализовать:
1. **Пер-строчный TTL и Generation из колонок DataFrame**:
   * Опция `aerospike.ttlColumn`: позволяет задавать индивидуальный TTL для каждой записи прямо из целочисленной колонки DataFrame (например, когда у разных событий разное время жизни).
   * Опция `aerospike.generationColumn` (`EXPECT_GEN_EQUAL` / `EXPECT_GEN_GT`) для оптимистичных блокировок (CAS) при записи.
2. **Массовое удаление записей (`aerospike.writeMode = "delete"`)**:
   * Быстрое пакетное удаление ключей из Aerospike (`BatchOperation::delete`) по DataFrame, содержащему только колонку первичного ключа `keyColumn`.
3. **Атомарные операции над числами и коллекциями (CDT Operations)**:
   * Режим `operate`: возможность указать для отдельных колонок атомарное сложение (`operations::add` для счётчиков) или добавление элементов в существующий `List` / `Map` (`cdt_list::append_items`, `cdt_map::put_items`) без чтения записи на клиент.
4. **Сжатие Arrow IPC (`LZ4_FRAME` / `ZSTD`) между Spark и Proxy**:
   * Включение компрессии буферов `RecordBatch` (`IpcWriteOptions` с `ZSTD` или `LZ4`) в Arrow Flight. Это снизит нагрузку на сеть между кластером Hadoop/Spark и прокси в 3–5 раз на текстовых и вложенных структурах.

## Релиз `v0.4.0` — Клиентская отказоустойчивость, авто-дискавери и динамический Rate Limiting

При длительных многочасовых выгрузках из Spark отдельная нода прокси может перезапуститься или попасть под обслуживание, а кластеру Aerospike может потребоваться контролируемый лимит RPS (чтобы не просаживать латентность онлайн-читателей).

### Что планируется реализовать:
1. **Прозрачный Failover на стороне `spark_connector` при падении ноды прокси**:
   * Если во время отправки батча в `AerospikeFlightDataWriter` одна из нод `flight.hosts` разрывает соединение, воркер на экзекьюторе автоматически переключается на живую ноду прокси и переотправляет неподтверждённый `RecordBatch` без падения всей Spark-таски.
2. **Авто-дискавери топологии прокси через Raft**:
   * Достаточно указать один seed-адрес в `flight.hosts`: коннектор при старте запрашивает актуальный список всех живых `flight_addr` из Raft (`get_cluster_status`) и балансирует потоки с учётом текущей загрузки каждой ноды прокси (`in_flight_records`).
3. **Распределённый Rate Limiter (квотирование RPS / пропускной способности)**:
   * Возможность задать глобальный лимит записей в секунду (`writer.max_records_per_sec` на уровне прокси или `connector.rateLimitPerSec` на уровне джоба), чтобы фоновая выгрузка из Hadoop гарантированно не влияла на p99 латентность фронтовых сервисов, читающих из Aerospike.
4. **Dead-Letter Queue (DLQ) для «битых» записей**:
   * Опциональный режим, при котором единичные записи с ошибками данных (например, ключ превышает лимит размера или невалидный формат) не роняют весь многомиллионный Spark-джоб, а складываются в отдельный отчёт в Raft / DLQ.

## Релиз `v0.5.0` — Enterprise-функции: персистентный Raft, мульти-аккаунты и OpenTelemetry

### Что планируется реализовать:
1. **Персистентное хранение Raft-лога и снэпшотов на диске (`raft.data_dir`)**:
   * Сохранение `current_term`, `voted_for`, WAL-лога и компактных снэпшотов `ClusterMetadataState` на диск, чтобы при полном рестарте всех нод прокси история и статусы джобов сохранялись в рамках настроенного `job_stats_ttl_secs`.
   * Автоматическая компактификация (log compaction) Raft-лога после снятия снэпшота.
2. **Мульти-пользовательская авторизация и ACL по Namespace**:
   * Поддержка списка пользователей в конфиге (`[[auth.users]]`) с разграничением прав доступа к конкретным `namespace` и `set` (например, команда аналитики может писать только в `namespace = "analytics"` или запускать только `dq`-проверки).
3. **Сквозной распределённый трейсинг (OpenTelemetry)**:
   * Проброс `traceparent` от драйвера Spark через экзекьюторы (`DoPut`) в `proxy_server` и экспорт спанов в Jaeger / Tempo для визуализации времени конвертации Arrow, ожидания в очереди семафора и времени ответа узлов Aerospike.
